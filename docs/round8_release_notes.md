## 2. 现场三大故障根因与修复说明

### 故障 1：OSL 激活后无法进行背景采集
- **现场现象**：在地面站向导中完成 2-port OSL 校准并点击“激活”后，校准向导的模式下拉框变灰或会话清空，无法继续执行“采集背景（Through/Air）”；若尝试再次校准，原 OSL 状态被覆盖或丢失。
- **根因分析**：
  1. 旧代码中 OSL 会话与背景会话混用单一 `_cal_id` 状态；
  2. 激活 OSL 后，地面站将向导置为已完成终态，并关闭了开始校准按钮；
  3. 空中端在激活背景时直接覆盖了 `active_calibration_id`，导致 OSL 求解参数被背景冲掉。
- **修复方案**：
  1. **双会话正交解耦**：将 OSL 身份（`active_osl_id`）与背景身份（`active_background_id`）在空中黑匣子与地面向导中严格分离；
  2. **向导状态机解锁**：OSL 求解激活后，模式下拉框与“开始校准”按钮立即恢复可用，支持连续新建并进入背景采集流程；
  3. **状态持续展示**：已生效的 OSL 校准 ID 与端口信息在地面站设备面板持续常驻显示，激活背景时绝不清除 OSL 身份；
  4. **跨域保护**：激活新 OSL 时，自动使旧背景失效，并在通过采集时正确注入 `through_measurement`，杜绝外推失真。

---

### 故障 2：地面无法使用既有校准文件（导入与导出）
- **现场现象**：现场已有以前标定好的标准校准文件（如 `solt_2port_*.json`），但在地面站无法将其下发至空中计算棒生效；空中计算棒上的校准也无法导出到地面站留存。
- **根因分析**：
  1. 缺少空中/地面双向校准文件传输协议；旧协议仅能控制在线采集步骤，无文件级别同步通道；
  2. 缺少校准文件的合法性检验，容易因文件格式或尺寸问题造成黑匣子崩溃；
  3. 空中端缺乏持久化配置原子回写与重启自动恢复机制。
- **修复方案**：
  1. **完整远程协议扩展**：
     - 新增 `cal_import_file`：地面站读取本地 JSON 并完整传输至空中端；空中端验证通过后原子写入 `_calibration/imports/`，更新 `air_config.json` 的 `calibration_path` 并即时生效；
     - 新增 `cal_export_file`：空中端将当前生效的校准文件内容完整回传给地面站，地面站弹窗保存或按请求落盘；
     - 新增 `cal_query_active` 与 `cal_clear_active`：支持查询空中当前生效校准详细元数据及按需单独清除背景/全部校准。
  2. **10MB 门控与严格数据校验**：
     - 双端统一校验器 `validate_calibration_content`：严格执行 UTF-8 字节数 $\le 10\text{MB}$ 上限，检验频率单调递增、点数范围（$\le 50000$ 点）、数值有限性（严禁 NaN/Inf）；
  3. **原子持久化与安全回滚**：
     - 导入落盘采用 `.tmp` 文件替换机制；若 `save_config` 失败，可靠回滚配置并恢复原文件旧字节，向客户端明确报告 `failed`，杜绝假生效。

---

### 故障 3：P1_Open 重采被拒且 UI 长期显示“请求采集中…”
- **现场现象**：在进行 OSL 步骤采集时，若某一步骤（如 P1_Open）采集质量不满意，点击“重新采集”后请求被拒绝，界面各按钮变灰并永久卡在“请求采集中…”，向导无法推进也无法取消。
- **根因分析**：
  1. 旧代码中正在采集或已完成步骤被视作不可变，空中端直接拒绝重采指令；
  2. 地面端发送重采后将步骤标记为“请求采集中…”，但在收到拒绝 ack 时未恢复控件可用性；
  3. 缺乏采集完成确认机制：步骤收尾需要时间，若过早发送下一步会产生并发冲突；若迟到回执到达则扰乱后续步骤；
  4. 看门狗机制不完善，未绑定请求生命周期，导致超时误判或无法唤醒。
- **修复方案**：
  1. **受控重采机制**：
     - `cal_capture` 携带 `recapture=True` 显式标志，空中端接纳重采并自动对旧样本归档存证（`capture_<step>_r<attempt>_<i>.npz`），作废旧解算；
  2. **权威 `step_done` 握手**：
     - 空中端采集线程在完成样本采集且执行 `close_current()` 彻底收尾进入 idle 后，权威发出 `step_done` 回执帧；
     - 地面站收到 `step_done` 后，自动平滑推进至首个未完成步骤；
  3. **看门狗令牌与 128 项幂等防卡死**：
     - 引入与 `(cal_id, request_id, step)` 三元组严格绑定的滑动看门狗令牌，在生命周期边界自动失效；
     - 收到拒绝回执或超时，地面端立即将步骤行回退至前序状态，清除“请求中…”标记，恢复指引与全部控件可用性；
     - 空中端维护 128 项有限 `request_id` 缓存，彻底杜绝迟到重放包串单。

## 4. 双端配套升级与部署操作指引

> **特别声明**：  
> 1. 本次修复涉及底层通信协议与双端状态机协同，**地面站与空中端必须同时升级替换为 20261013 配套版本**！切勿单端混用新旧版本。  
> 2. 本便携包绝不在构建时执行真实部署，**严禁私自注册或运行 Windows 自启动任务（`schtasks`）**，必须由现场运维人员在确认硬件状态后手动替换。

### 4.1 地面站升级步骤（地面测控电脑）
1. 完整关闭正在运行的旧版地面站程序窗口及黑色命令行窗口；
2. 将 `地面站便携包_20261013_校准修复.zip` 解压到地面电脑工作盘（如 `D:\地面站便携包`）；
3. 确认网卡 IP 保持为 `192.168.144.20`（子网掩码 `255.255.255.0`），可通过运行 `【查看本机IP(地面站)】.bat` 检查；
4. 双击 `run_ground_station.bat` 启动新版地面站；
5. 进入“空中端设备”面板，确认与计算棒正常建连。

### 4.2 空中端黑匣子升级步骤（机载计算棒）
新版升级脚本已采用**非 purge 安全复制策略**（基于 `robocopy /E`，且 `/XF air_config.json`），**绝对保护原有配置、实测校准文件与历史日志不被删除**。

1. 远程登录或将计算棒连接屏幕/键鼠；
2. 将 `空中端黑匣子便携包_20261013_校准修复.zip` 解压至计算棒临时目录（如 `D:\pkg_update`）；
3. 打开命令行或双击运行 `升级_替换程序.bat`，并传入旧版程序目录路径（例如 `C:\UAVGPR_AirBlackBox`）；
4. 升级脚本将自动执行：
   - 停止当前运行的后台任务与 `pythonw` 进程；
   - 完整备份旧版本到 `_backup_时间戳` 文件夹；
   - 安全同步新版程序文件，**严格保留 `air_config.json`、`logs\`、`gpr_runs\`、`_calibration\`、`calibrations\` 及所有 `.npz`/`.json` 数据文件**；
   - 自动重新启动后台服务。
5. 在地面站界面观察“程序版本”，确认显示为 `8.0.0-round8`。

## 5. 现场真机复核边界清单

自动化全量回归与模拟硬件测试已证明**软件层面的协议、状态机、数据流与数学算法 100% 正确且健壮**。由于自动化测试环境不具备真实微波天线、实物标准校准件及真实无人机飞行动力，交付后在现场真机联调时，请重点复核以下物理层项目：

1. **网络通信物理连通性**：
   - 检查机载 HM30 天空端与地面端网线水晶头牢固度；
   - 验证地面站 `192.168.144.20` 与计算棒 `192.168.144.21` 的 `ping` 延迟与稳定性。
2. **LibreVNA USB 硬件与供电**：
   - 确认 LibreVNA 两个端口射频电缆连接紧固无松动；
   - 确认计算棒 USB 端口供电充足（避免因瞬态低压导致 USB 断开重连）。
3. **GNSS 物理天线与星历定位**：
   - 确认 GNSS 模块串口波特率配置为现场硬件默认值（9600）；
   - 在室外开阔场地确认搜星状态（通过 `run_gnss_check.bat` 确认 10 秒只读诊断输出）。
4. **校准件实物测量**：
   - 进行 2-port OSL 校准时，确保实物 Open、Short、50Ω Load 标准件螺套紧固；
   - 校准完成后，观察地面站回传的 S11 曲线反射幅度是否符合物理预期（Load 在全频带应有良好的回波损耗，Open/Short 应接近全反射）。
5. **机载存储水位**：
   - 检查计算棒硬盘剩余空间，确保大于 20GB 水位阈值。
