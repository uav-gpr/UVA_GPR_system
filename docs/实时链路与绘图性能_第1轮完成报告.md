## 5. 修改前确认的性能根因（复核结论）

1. **主线程 NPZ 解压**：`on_trace` 在 Qt 主线程 `np.load` 解压 + 全部 schema 校验 + metadata 解析（201频点/2048时域双通道实测 ~2ms/条，遇 GC 或压缩高峰更高）。
2. **全历史矩阵重构**：`_bscan_matrix_for_display` 每条 Trace `np.column_stack(全部历史)`——1000 道历史实测 p50 ≈ 30ms（flat 关）/29ms（flat 开），且随历史线性增长；两通道 ×2。
3. **全历史 Flat Filter**：同上，每条 Trace 对全部历史滤波。
4. **autoLevels=True + 每条 Trace setLookupTable + 矩阵转置复制**。
5. **GNSS 地图每个有效 Fix 都 runJavaScript**（WebEngine 进程间调用，非主线程但产生排队压力）。
6. **空中端 drop_incoming 队列**：消费稍慢即静默丢 Trace（帧率低且数量对不上账）。
7. **停止后 2 秒放弃残留** + 地面端过早显示"已停止"（"停止后又来一条 Trace"的直接解释：队列/Qt 事件队列中仍有数据）。

症状"两条快显然后停顿"与 2+3 的历史长度增长（每 64 道重构成本台阶式上升）+ 主线程串行解码一致。

## 7. 默认无间隔模式语义（interval_s=0）

- 底层兼容表示 `interval_s=0.0`；UI 显式显示"每个完整Sweep（默认）"。
- 每个完整有效 sweep 全部选择；USB 线程不 sleep、不按显示帧率抽样、不因处理慢丢弃（无损队列）。
- 复用既有 `FixedIntervalSweepSelector._select_every`（未修改）。
- 空中端 interval spin 默认 0；地面端 AcquisitionUiSettings 默认 0.0；两者一致。

## 8. 固定间隔模式语义（interval_s>0）

- LibreVNA 后台连续扫频；第一条有效 sweep 立即选择；`next_due = first + interval`（固定 monotonic deadline，禁止 `now+interval` 漂移）；选择达到 deadline 后的第一条完整有效 sweep；跨多 deadline 只选一条并计 missed_slots。
- 中间未选择 sweep 计入 scheduler skipped/missed（非损坏、非队列丢失）。
- USB 线程无 sleep（AcquisitionWorker 旧 legacy 路径的 sleep 保留但连续模式不使用）。
- 全部由既有 `FixedIntervalSweepSelector` 实现（本轮零修改），测试既有覆盖 20+ 条。

## 9. 无损队列、高水位和受控停止

- `LosslessProcessingQueue`（默认 512 条 ≈ 201频点 sweep 数 KB/条，内存可忽略；20s 消费缓冲 @25Hz）。
- 高水位（0.75×maxsize）：即时告警（status 信号），不停止。
- 硬上限：**先接收当前 Trace**（有界阻塞等待消费者，默认 30s 极限），触发 `stop_requested` + `on_hard_limit` → worker `request_stop` 在完整 sweep 边界受控停止新采集 → 消费者排空全部已选数据 → 报告 drained（对账 selected==processed）。
- **明确声明**：生产速度长期高于消费速度时，有限内存无法无限保证持续采集；本策略是"告警＋受控停止新采集＋完整排空"，绝不静默丢失。受控停止以 `_controlled_stop_reason` 记录并随 acquisition_status 上报，不伪装正常完成。
- 有限 count 语义不变：到达 count 停止选择，已选数据全部排空。

## 10. Stop/drain 状态机

```
采集中(acquiring)
  └─ stop 命令 / count 到达 / 受控停止 → 停止新采集(stopping：向地面发 acquisition_status, 含队列深度)
       └─ ProcessingConsumer: draining（排空到队列为空，无时限；逐条处理/保存/入发送队列）
            ├─ 全部成功 → drained → 向地面发 stopped(processing_queue_depth=0) → finished_run
            └─ 任一失败 → drain_failed（逐条 failed 上报 + worker failed.emit 汇总）→ 明确"排空失败"
```

- 地面端：command_ack(stop) → "正在停止（等待排空）"；acquisition_status(stopped & depth=0) → "已停止（数据已全部排空）"。
- 排空中持续可见队列深度（状态标签 + 诊断日志）。

## 11. RemoteSender 补传与地面去重

**补传**：
- 正常任务停止不停止 sender（跨任务继续运行，FIFO 逐条 ACK 后才算发送完成；断线保留 pending 并重连重试——原有逻辑保留）。
- 程序正常关闭：`stop(drain=True)` 先排空发送队列（MainWindow closeEvent 等待至多 30s），超时则拒绝关闭并保留引用重试（不伪装安全关闭）。
- **未实现磁盘 outbox**。现有机制覆盖：任务停止、网络瞬断（重连补传）、程序正常关闭（优雅排空）。未覆盖故障范围（诚实声明）：进程崩溃/被杀、正常关闭时网络长时间断开（30s 排空超时后用户强制退出）、系统断电。这些场景下发送队列会丢失（本地 NPZ/CSV 已保存，可事后人工补传）。理由：磁盘 outbox 需要原子写、ACK 回执持久化、重启扫描与 run_id/trace_index 续传协议，属于独立的可靠性工程，建议第2轮与常驻采集服务一起实现（见 §18）。

**去重**（地面 ReceiverThread._accept_trace）：
- 唯一身份：`(run_id, trace_index)` + sha256。
- 首次：校验、保存、ACK、进解码/显示。
- 完全相同重传：ACK（duplicate 标记），不再写 metadata、不再进 B-scan/显示。
- 同编号不同 sha256：拒绝（不 ACK）、记录错误、保留已存文件。
- 重启后：同编号 trace 落盘文件已存在 → 不重复写；`_seen_traces` 内存集合重建依赖重传包的 sha 与已存文件对比的完整跨重启冲突检测为**尽力而为**（未存 sha 索引文件；本轮明确标注限制）。

## 12. 修改前后性能数据对比

**B-scan 显示矩阵构造**（201频点/2048时域点/64道窗口，`docs/bench_round1_baseline.py`，纯 NumPy，无 GPU 绘制）：

| 历史 | 旧路径 flat关 p50 | 新路径 flat关 p50 | 旧路径 flat开 p50 | 新路径 flat开 p50 |
|---|---|---|---|---|
| 64 道 | 2.00ms | 0.29ms | 2.01ms | 2.24ms |
| 100 道 | 2.69ms | 0.30ms | 2.70ms | 2.40ms |
| 1000 道 | **30.07ms** | **0.35ms** | **29.21ms** | **2.50ms** |

- 历史从 64→1000 道：旧路径 15 倍线性增长；新路径 flat 关 ~持平（0.29→0.35ms，非总道数线性）；flat 开受窗口+邻域约束（2.2→2.5ms）。
- 注：每条 Trace 需 S11/S22 两通道 ×2；旧路径 1000 道仅矩阵即 ~60ms/条 > 40ms 预算（25Hz），是卡顿主因。
- 真实 GPU 屏幕绘制未测量（offscreen 无 GPU 合成）；区分：纯 NumPy 矩阵耗时（上表）/ Qt 调用提交耗时（下表 setImage 全链）/ 真实屏幕绘制（未验证）。

**同机 loopback 端到端**（`docs/bench_round1_loopback.py`：500 条 × 25Hz × 20s，201频点/2048时域/S11+S22，RemoteSender→TCP→ReceiverThread→后台解码→FIFO→Qt 提交）：

| 指标 | 数值 | 目标 |
|---|---|---|
| 数量对账 | sent=accepted=decoded=displayed=**500/500** | 全等 |
| ground_decoded（解码线程）p50/p95/max | 2.02/2.48/20.5 ms | — |
| ground_displayed（Qt 主线程提交）p50/p95/max | 2.24/**3.58**/4.13 ms | p95≤20ms ✅ |
| 端到端（air入队→地面显示提交）p50/p95/max | 120.3/**131.2**/133.8 ms | p95≤200ms ✅ |
| 显示 FIFO 峰值 | 2 | 无积压 |

- 端到端 p50≈120ms ≈ 3 个 40ms 周期：逐条 ACK 的 stop-and-wait 流控（1 条在途）+ 25Hz 发送节流是主要构成，不是处理瓶颈。
- 同进程同一 perf_counter 时钟；真实无线跨机场景该口径需两端系统时钟同步（UTC），未验证。
- 修改前同场景无法直接测得可比数据（旧链路无 FIFO/无阶段计时）；以 §5 根因分析 + 矩阵基准（1000 道历史单条 ~60ms 仅矩阵构造）作为修改前基线证据。

## 13. selected/processed/saved/sent/displayed 对账

loopback 基准（同 §12）：selected(air)=500，processed(消费者)=500（含本地保存与遥测入队），sent=500，ground accepted(新增保存)=500，ground decoded=500，ground displayed=500——全链路 500:500:500:500:500:500。慢消费者单测（`test_trace_index_survives_queue_pressure`）另证 processed==selected 且 drain_state=drained。

## 17. 已知限制和遗留风险

1. **磁盘 outbox 未实现**（§11 已列未覆盖故障范围）。
2. 跨重启的同编号 sha 冲突检测为内存集合 + 文件存在性，未持久化 sha 索引。
3. LosslessProcessingQueue 硬上限阻塞默认 30s 极限：消费者完全卡死时 USB 线程会阻塞至该上限（之后 put 返回 False 触发受控停止；item 本身不丢，但该极端场景未设计优雅路径——实际卡死消费者会由 fatal/排空失败路径覆盖）。
4. 首轮实现中发现并修复的缺陷（记录）：`apply_flat_filter_windowed` 裁剪列数越界广播错误；`bscan_window_from_rows` 空 history/显式 n_samples 校验缺失；Lossless 队列 hard-limit 仅在预检查路径触发（put 填满时不触发）；worker finally 访问自定义 consumer 的 drain_state 属性导致顽固消费者场景 finished_run 丢失；排空阶段失败未上报 worker。
5. 日志：每条 Trace 一行"已收到 Trace N"保留（既有测试契约 + maximumBlockCount 2000 限增长）；高频**状态**已改为计数/告警节流。
6. p95 端到端 131ms 的主要构成是逐条 ACK stop-and-wait；若未来需要 <50ms 需改为滑动窗口 ACK（改变协议语义，属后续轮次）。
